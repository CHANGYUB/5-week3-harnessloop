# 코드 리뷰 Agent — 구현 설명

---

## 무엇을 만들었나

Python 코드 파일을 받아서 자동으로 코드 리뷰 보고서를 생성하는 AI 에이전트입니다.

단순히 "이 코드 리뷰해줘"라고 GPT에 붙여넣는 방식과 다르게, 이 에이전트는 코드를 직접 파일에서 읽고, 파이썬 AST(추상 구문 트리)로 메트릭을 측정하고, 위키백과에서 관련 모범 사례를 찾아서, 마지막으로 마크다운 표와 ASCII 막대 그래프가 포함된 구조화된 보고서를 만들어냅니다. 보고서는 파일로도 자동 저장됩니다.

---

## 왜 코드 리뷰 Agent를 선택했나

코드 리뷰는 실제로 반복적인 판단이 필요한 작업입니다. 함수 하나만 봐서는 안 되고, 전체 파일 구조, 함수 길이, 인자 수, 주석 유무 같은 정량 지표와 설계 원칙 같은 정성 판단을 함께 해야 합니다.

그래서 이 작업이 "모델이 Tool을 선택해서 순서대로 정보를 수집하고, 그 결과를 바탕으로 최종 판단을 내리는" Agent 구조에 잘 맞는다고 봤습니다. 미리 정해진 순서대로 함수를 호출하는 게 아니라, 모델이 "파일을 먼저 읽어야겠다 → 메트릭을 분석해야겠다 → 모범 사례를 찾아보자"는 판단을 스스로 내리게 됩니다.

출력에 표와 그래프를 요구한 이유는, 텍스트만 가득한 리뷰는 실제로 읽기 불편하기 때문입니다. 함수별 라인 수를 ▓ 기호로 시각화하거나, 문제점을 심각도(🔴/🟡/🟢)로 분류하면 리뷰어와 개발자 모두 한눈에 우선순위를 파악할 수 있습니다.

---

## Tools — 4개를 어떻게 구성했나

### Tool 1: `read_code_file`

코드 파일을 읽어오는 가장 기본적인 도구입니다. 베이스라인의 `read_file`과 동일한 방식이지만, 보안 처리를 직접 구현했습니다. 저장소 루트 바깥 경로나 `.env` 같은 숨김 파일에 접근하면 에러를 냅니다. 모델이 임의의 경로를 시도해도 안전하게 막히게 됩니다.

### Tool 2: `analyze_code_metrics`

이 도구가 이번 구현의 핵심입니다. Python의 `ast` 모듈로 코드를 파싱해서 함수 수, 클래스 수, 각 함수의 라인 수, 인자 수, 독스트링 유무를 JSON으로 반환합니다. 모델한테 "이 코드 복잡해 보여"라고 느낌으로 말하게 하는 게 아니라, 실제 숫자를 도구로 측정해서 넘겨주는 겁니다. 그래야 "함수 A는 43줄이고 인자가 7개라 복잡하다"는 근거 있는 리뷰가 나옵니다.

Python 파일이 아닌 경우에는 AST 파싱 대신 라인 수만 세서 반환하도록 분기 처리했습니다. 모든 파일에 대응하되, Python일 때 가장 풍부한 정보를 제공합니다.

### Tool 3: `search_best_practices`

베이스라인의 `wikipedia_search` 함수를 그대로 재사용했습니다. 새로 만들기보다 검증된 코드를 가져오는 게 맞다고 판단했습니다. 위키백과에서 "Python 클린 코드", "단일 책임 원칙" 같은 개념을 검색해서 리뷰에 근거를 더합니다.

### Tool 4: `save_review_report`

완성된 리뷰를 `assignment/Changyub/reviews/` 폴더에 저장합니다. 이 도구가 없으면 에이전트가 리뷰를 생성해도 그냥 출력하고 사라집니다. 저장 도구를 Tool로 만들어두면 모델이 스스로 "보고서를 저장해야겠다"고 판단해서 호출하게 됩니다. 즉, 저장이 워크플로우의 일부로 자연스럽게 편입됩니다.

## Agent Loop — LangChain `create_agent`를 선택한 이유

과제 요구사항이 LangChain 기반 구현이었고, `create_agent`가 Tool Loop를 자동으로 관리해줘서 선택했습니다.

직접 구현하면 "모델 호출 → Tool Call 파싱 → Tool 실행 → 결과를 메시지에 추가 → 다시 모델 호출"을 반복하는 루프를 손으로 짜야 합니다. `create_agent`는 이 루프를 내장하고 있어서, Tool을 등록하고 `invoke`만 하면 모델이 필요한 Tool을 선택해서 순서대로 호출합니다.

실제 실행 로그에서 모델이 `read_code_file → analyze_code_metrics → search_best_practices` 순서로 호출하는 걸 볼 수 있는데, 이 순서는 코드에 정해놓은 게 아니라 모델이 판단한 겁니다.

## Harness — 실행을 어떻게 제한하고 관찰했나

Harness는 Agent 바깥에서 실행을 제어하는 안전장치입니다. 4가지를 구현했습니다.

**Execution Budget (`recursion_limit=40`)**
LangGraph는 노드 실행 횟수를 재귀 깊이로 제한합니다. 40으로 설정해두면 Agent가 Tool을 무한히 호출하거나 무한 루프에 빠지는 걸 막을 수 있습니다. 이게 없으면 모델이 Tool을 계속 호출하거나 verify-feedback 루프를 계속 돌면서 API 비용이 무한정 나갈 수 있습니다.

**Timeout (`ChatOpenAI(timeout=30.0)`)**
모델 응답이 30초를 넘으면 예외가 발생합니다. 네트워크 문제나 모델 부하 상황에서 프로세스가 영원히 멈춰있는 걸 방지합니다.

**Error Handling (`try/except`)**
`run_agent_with_harness` 함수 안에서 모든 예외를 잡습니다. 오류가 나도 프로그램 전체가 중단되지 않고, 오류 내용을 Trace에 기록한 뒤 빈 결과를 반환합니다. Loop Engineering 입장에서는 "오류 = 실패한 실행"으로 처리되어 재시도 카운트에 포함됩니다.

**Trace (`RunTrace` 데이터클래스)**
어떤 Tool이 어떤 인자로 호출됐는지를 순서대로 기록합니다. 실행이 끝나면 전체 Tool 호출 목록과 오류 개수를 요약해서 출력합니다. 이게 있어야 "모델이 실제로 어떤 판단을 내렸는지"를 나중에 확인할 수 있습니다.

## Loop Engineering — 왜 검증과 재실행이 필요했나

Agent가 리뷰를 한 번에 완벽하게 만들어주기를 바랄 수는 없습니다. 특히 "표를 반드시 포함해라", "▓ 그래프를 그려라" 같은 구체적인 형식 요구사항은 모델이 처음에 빠뜨리는 경우가 많습니다.

그래서 생성 → 검증 → 피드백 → 재생성의 루프를 구현했습니다.

**검증 단계 (`verify_review`)**
규칙 기반으로 체크합니다. 표 행이 4개 이상인지, ▓ 문자가 있는지, 심각도 마커(🔴/🟡/🟢)가 있는지, 섹션이 3개 이상인지, `read_code_file`과 `analyze_code_metrics`를 실제로 호출했는지를 확인합니다. 이 검사들은 리뷰의 "형식 완성도"를 보장합니다.

**LLM Evaluator**
규칙 검사를 통과하더라도, 내용 자체가 엉터리일 수 있습니다. 그래서 별도의 모델 호출로 "코드에 근거한 문제점이 있는가", "실행 가능한 개선 제안이 있는가", "지어낸 정보가 없는가"를 평가합니다. 생성 모델과 평가 모델을 분리한 건, 자기 자신을 평가하게 하면 항상 좋다고 답하는 경향이 있기 때문입니다.

처음에 Evaluator 프롬프트를 "명확한 개선점이 있을 때만 fail"로 모호하게 썼더니, 모델이 "더 좋아질 수 있다"는 이유로 항상 fail을 반환했습니다. 이건 LLM Evaluator 설계에서 흔히 만나는 문제인데, 해결책은 pass 조건을 열거형으로 명시하고 "개선 여지가 있어도 기준을 충족하면 pass"라고 명확하게 선을 긋는 겁니다.

**Feedback & Re-run**
검증이 실패하면 어떤 부분이 문제인지를 `HumanMessage`로 만들어서 대화 히스토리에 추가합니다. 다음 Agent 실행 때 모델은 이전 리뷰와 피드백을 모두 context로 받게 되어서, 이전에 빠뜨린 부분을 보완한 리뷰를 다시 씁니다. 이전에 읽은 파일 내용이 메시지 히스토리에 남아 있어서 Tool을 다시 호출하지 않아도 됩니다.

**Loop Limit (`MAX_RUNS=3`)**
무한 재시도를 막기 위해 최대 3회로 제한했습니다. 3번 모두 실패하면 그 시점까지의 최선의 결과를 출력하고 종료합니다. 실제로는 형식 요구사항을 갖춘 리뷰가 나오면 1~2회 만에 통과하도록 설계되어 있습니다.

## LangGraph로 루프를 구현한 이유

검증-피드백-재실행 루프를 `while` 루프로 짜면 관리가 어려워집니다. 상태를 어디에 보관할지, 종료 조건을 언제 체크할지, 피드백을 어떻게 다음 실행에 전달할지를 모두 직접 관리해야 합니다.

LangGraph는 이 루프를 노드와 엣지로 표현합니다.

- `agent` 노드: 모델에게 Tool 사용 또는 리뷰 작성을 요청
- `tools` 노드: Tool을 실제로 실행
- `verify` 노드: 리뷰 품질을 검증
- `feedback` 노드: 피드백을 메시지로 추가

노드 사이의 이동을 조건 함수로 제어합니다. `agent` 다음에 Tool Call이 있으면 `tools`로 가고, 없으면 `verify`로 갑니다. `verify` 다음에 통과하거나 3번을 채우면 종료, 아니면 `feedback`으로 갑니다.

이 구조를 그림으로 그리면 바로 실행 흐름이 보이고, 각 노드를 독립적으로 테스트하거나 교체할 수 있다는 장점이 있습니다. `InMemorySaver`를 붙이면 같은 thread_id로 실행한 대화 히스토리가 저장되어, 피드백 사이클에서 이전 내용을 자동으로 참조합니다.

## 정리

| 설계 결정 | 이유 |
|---|---|
| Tool 4개 구성 | 코드 읽기·분석·검색·저장이 각각 독립적인 책임을 가짐 |
| AST 메트릭 분석 | 느낌이 아닌 실제 숫자로 리뷰 근거를 만들기 위해 |
| 위키백과 재사용 | 검증된 베이스라인 코드를 그대로 활용 |
| LangGraph로 루프 구현 | while 루프보다 상태 관리와 흐름 제어가 명시적 |
| Evaluator 분리 | 생성 모델이 자기 출력을 평가하는 편향을 피하기 위해 |
| Evaluator pass 조건 명시 | 모호하면 LLM이 항상 개선점을 찾아내기 때문 |
| recursion_limit=40 | Tool 호출 무한 반복 방지 |
| MAX_RUNS=3 | 검증 루프 무한 반복 방지 |
